# nmavitobot v10

Пять Avito-аккаунтов:
- Агрегаты — кошелёк + аванс
- Авмекс — кошелёк + аванс
- Надёжные Машины (оранжевые) — кошелёк + остаток размещений
- Надёжные машины (синие) — кошелёк + остаток размещений
- ТИР — кошелёк + аванс

Также:
- статусы объявлений;
- дата окончания тарифа, если Avito её отдаёт;
- следующий запланированный тариф: дата + стоимость, если Avito его отдаёт;
- сообщение удаляется через 10 минут;
- кнопка «Обновить» удалена;
- `/start` и `/status` сразу показывают кэш, обновление идёт в фоне.

Секреты в репозиторий не добавлять.


## v12: сначала финансы, потом объявления

Обновление теперь идёт в две фазы:

1. Сначала по всем аккаунтам собираются кошелёк, аванс/остаток размещений и тарифные данные.
2. Только после этого начинается тяжёлый обход всех страниц объявлений.

Это позволяет быстро получить диагностические и финансовые данные по Авмексу, ТИР и другим аккаунтам, не ожидая полного обхода тысяч объявлений предыдущего аккаунта.


## v13: исправлен показатель «Аванс»

Для CPA-аккаунтов показатель «Аванс» теперь берётся из поля `balance`
метода `/cpa/v2/balanceInfo`.

Поле `advance` больше не используется для отображения, потому что оно
не соответствует цифре «Аванс» в интерфейсе Avito Pro.

Сумма приходит в копейках и преобразуется в целые рубли без округления вверх,
как в интерфейсе Avito Pro.


## v14: двухэтапное обновление Telegram

Раньше финансы собирались первыми, но сообщение в Telegram редактировалось только
после полного обхода всех объявлений. Поэтому после строки `Financial phase completed`
визуально казалось, что бот завис.

Теперь:
1. После завершения финансовой фазы сообщение сразу редактируется.
2. Пока считаются объявления, в блоках показывается `Объявления обновляются…`.
3. После полного обхода объявлений то же сообщение редактируется второй раз.


## v15: подписки CPA-аккаунтов

Добавлены известные подписки:
- Агрегаты — Максимальная
- Авмекс — Расширенная
- ТИР — Расширенная

Для этих CPA-аккаунтов больше не вызывается `/tariff/info/1`, потому что этот
метод возвращает 404 и относится к другому типу тарифа. Это убирает лишние
ошибки из логов и немного ускоряет финансовую фазу.

Название подписки хранится в `config.json` и выводится строкой `Подписка: ...`.


## v16: сроки подписок — диагностика источника

Из интерфейса убрана строка только с названием подписки: без даты окончания она
не решает задачу.

Для транспортных тарифов надпись `Следующий тариф` заменена на
`Следующий платёж`.

Для CPA-аккаунтов добавлена диагностика истории операций:
`POST /core/v1/accounts/operations_history/` за последние 35 дней.
В лог выводятся только операции, связанные с подпиской. Это нужно, чтобы
проверить, содержит ли доступная нашим ключам история точную дату/период
подписки и не придумывать срок окончания.


## v17: исправлена диагностика подписок

Исправлена структура ответа `operations_history`: список операций может находиться
в `result.operations`, а не на верхнем уровне ответа. В v16 это не учитывалось.

Также:
- даты запроса отправляются в RFC3339 с часовым поясом;
- в лог пишется `Bot started v17`;
- для каждого CPA-аккаунта пишется `Subscription scan v17 ...`;
- подпись `Следующий тариф` остаётся заменённой на `Следующий платёж`.


## v18: даты окончания CPA-подписок

Для Агрегатов, Авмекса и ТИР бот теперь:
- берёт последнюю операцию подписки из истории операций;
- использует 30-дневный период, заданный в `config.json`;
- показывает `Подписка до: ...`;
- показывает `Следующий платёж: дата — сумма`.

Сумма берётся из `amountRub` последней операции подписки.
Дата рассчитывается как дата последней операции + 30 дней.

Также при `/start` и `/status` отправляется `remove_keyboard=true`, чтобы удалить
старую постоянную клавиатуру с кнопками `Обновить` / `Поток`.


## v19: строки подписки в конце блока аккаунта

Для CPA-аккаунтов строки:
- `Подписка до: ...`
- `Следующий платёж: ...`

перенесены после статистики объявлений, в самый конец информации по аккаунту.


## v20: диагностика остатка размещений

Для транспортных аккаунтов `nm_orange` и `nm_blue` в лог теперь выводятся
все поля `current.packages[]` из `/tariff/info/1`.

Это нужно, потому что поле `remain`, на которое мы ориентировались по схеме API,
в реальном ответе этих аккаунтов отсутствует. После лога `Tariff package ...`
можно будет определить фактическое поле остатка размещений и добавить его в UI.


## v21: исправлено редактирование Telegram-сообщения

Причина `Bad Request: message can't be edited` найдена: статус отправлялся с
`ReplyKeyboardRemove`, а Telegram разрешает `editMessageText` только для сообщений
без reply markup либо с inline-клавиатурой.

Теперь:
- старая клавиатура `Обновить / Поток` удаляется отдельным временным сообщением;
- основной статус отправляется без reply markup и нормально редактируется;
- лог `Telegram updated ...` пишется только после успешного редактирования;
- итоговое сообщение удаляется через 10 минут после завершения фонового обновления.


## v22: глубокая диагностика остатка размещений

Фокус только на `nm_orange` и `nm_blue`.

Проверяются три источника:
1. `current.packages` и `scheduled.packages` в `/tariff/info/1`.
2. История операций с начала текущего тарифа — в частности `serviceType=lf`,
   `tariff`, `bundle` и операции с упоминанием размещений/пакетов.
3. Autoload v2: последние отчёты и `/items/fees`, где API может показать
   списания размещений из пакета (`fees_type=package`, `fees_amount`,
   `fees_package_id`).

Никаких расчётов остатка в интерфейс пока не добавляется: сначала нужно
получить реальные данные и проверить формулу.
